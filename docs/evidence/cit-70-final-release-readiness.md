## Fresh install and real 1.3.0-origin upgrade

The fresh site was a new WordPress 6.9.7 install using a new MySQL database and official WooCommerce 10.8.0 archive (SHA-256 `37acec830f566941e561e7e8da95b3b8182ac24f77513905e0ad15842ed11f5b`). It activated the staged payload, not repository source. `yoohw_cos_db_version=0.2.4`; `SHOW TABLES LIKE 'wp_yoohw_cos_%'` found 12 tables. Synthetic fixture APIs created order/customer linkage, one note, task, tag and static segment with both memberships. Browser inspection confirmed Customer Profile actions, RFM, attention, Saved Views, Customers controls, Diagnostics and Tasks. With WC temporarily inactive, the staged plugin still loaded, `WC_Order` was absent and the schema stayed `0.2.4`; WC was then reactivated.

The upgrade site was separately installed from repository tag `1.3.0`, before any current-tree activation. Tag code created completed USD WC order `#10` for a synthetic guest, customer `#1` with 1 order/$123.45, one order fact, note, order-linked task, tag and static segment with both memberships. The tag reported schema `0.2.1` and 11 tables. After deactivation, replacement with the staged product and reactivation, schema reached `0.2.4`/12 tables. `wc_get_order(10)` remained valid; customer identity/contact, order/fact and all four owned relationships remained. No Reset was used for this overlay.

Before background convergence the upgraded customer was `money_state=unknown`, `intelligence_currency_ready=0`; `identity_normalization_v2`, `commerce_facts_v2` and `commerce_currency_v3` were pending, and Diagnostics listed currency/migration attention with the migration cron scheduled. Ten calls to `YoOhw_COS_Migration_Runner::run_next_batch()` completed all three with zero pending/unresolved issues, preserved the USD order contribution, and changed the customer to `money_state=comparable`, `money_currency=USD`, current metrics policy version 2 and currency-ready 1. On the same disposable upgraded site, a bounded synthetic replay removed the completed currency ledger entry and set its existing order fact back to policy 1/NULL currency. `register_missing_currency_backfill()` then created pending `commerce_currency_v3`, scheduled cron and kept `money_is_comparable=false` until the next bounded batches restored the same comparable USD result. Removing the ledger entry alone when all facts were already current correctly did not schedule unnecessary work.

Exact-main integration tests `test_current_schema_recovers_missing_currency_backfill_and_old_issue_ledger`, `test_current_facts_still_retry_an_old_unattributable_issue` and related currency tests cover old `completed_with_issues` resolution, identityless no-fact behavior, existing-fact/lookup/conflict failures, true mixed-currency unavailability and no invented FX/store currency. The browser's separate fresh fixture had USD and EUR orders for one customer: Profile total/AOV and RFM M displayed unavailable while individual order totals kept their own currencies; a USD-only customer showed $88.75 after migration convergence. The initial USD-only browser view remained unavailable while migration was pending, then became comparable after completion. Overview revenue likewise failed closed with a mixed customer. CI assertions cover list/query/filter/export and RFM monetary agreement; this manual fixture sampled the rendered Profile and Overview paths rather than every export permutation.

## Historical state, package and control-plane limits

The actual `1.3.0` tag has no Saved Views, Reset Guard or privacy exporter/eraser/suppression implementation. Therefore no legitimate pre-overlay 1.3.0 record of those types exists to preserve; inventing one before overlay would make the required origin fixture a hand-shaped approximation. The meaningful forward-upgrade proof is that the real 1.3.0 customer/order/relationships survive overlay, and the newly introduced state then works and persists on that same upgraded site. A Saved View remained after plugin reactivation. An erasure of a separate synthetic subject exported two owned items before deletion, completed in five pages, left one suppression receipt, returned zero owned export items afterward and blocked routine resync while the WooCommerce order remained. Receipt and suppression survived plugin reactivation. A second erasure paused after page 1 with a real continuation row, survived reactivation, completed on page 8 and removed its continuation row. A deliberately interrupted Reset retained `pending` and the same epoch after reactivation, rejected ordinary writes, then `reset_data()` recovered with a different ready epoch; suppression receipts remained. This validates current state survival after overlay, not a fictitious pre-1.3 implementation.

Both distribution manifests and deterministic ZIP bytes matched. The allowlist selected the expected product entrypoint, admin/includes/assets/templates/languages, readme, changelog, uninstall and licenses. No `.git`, `.github`, tests, docs, scripts, Composer metadata, logs, archives, symlinks or runtime artifacts entered the payload. The staged tree activated and loaded. Release publisher contract tests passed. `main` protection required PRs, strict `YCI Required CI`, dismissed stale reviews and prohibited force-push/deletion at audit time. Repository release docs still require one-time Human configuration of the production Environment/credentials; this audit did not inspect secrets or exercise release workflows.
